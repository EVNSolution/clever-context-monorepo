# UI 구현 레슨

## 목적

운영형 화면을 만들 때 반복해서 깨졌던 레이아웃, 반응형, footer, 버튼 정렬 규칙을 current truth로 고정한다.

이 문서는 개별 화면 spec이 아니라 전역 구현 기준이다.

## 기록 타이밍

- 레슨은 작업 중간에 쓰지 않는다
- `완료 신호`를 보낼 수 있을 만큼 검증이 끝난 뒤에만 쓴다
- 배포가 있는 작업이면 배포 후에만 쓴다
- 임시 추정, 뒤집힐 수 있는 실험 관찰은 올리지 않는다

## 1. 헤더는 템플릿으로 올린다

- 같은 계열 화면의 헤더는 템플릿을 공유한다
- 페이지 첫 패널을 헤더처럼 쓰지 않는다
- 본문 요소는 헤더 바로 아래에 붙을 수 있어야 한다
- 한 화면에서 맞춘 헤더 리듬은 다음 화면에서 복제 가능한 템플릿이어야 한다

## 2. 운영 화면은 표와 작업이 중심이다

- 표보다 툴바와 장식이 먼저 보이면 실패다
- 흰 패널, 회색 계열 텍스트, 얇은 보더를 기본으로 쓴다
- 강조색은 선택 상태처럼 이득이 명확한 경우에만 쓴다
- 강조가 필요 없으면 무채색으로 간다

## 3. 중복 UI는 제거한다

- 페이지 전체 설명이 있으면 패널 안 동일 설명은 지운다
- 상단 개수, 하단 범위, 요약 칩처럼 같은 정보를 여러 번 반복하지 않는다
- 선택된 필터를 다시 칩으로 반복 노출하지 않는다
- 사용자가 이미 이해한 정보는 다른 영역에서 다시 과장하지 않는다

## 4. 반응형은 width와 height를 함께 본다

- 컨테이너는 viewport를 무조건 꽉 채우지 않는다
- 다만 컨테이너 내부 footer는 항상 컨테이너 최하단에 있어야 한다
- 행이 짧아도 footer는 위로 끌려 올라오면 안 된다
- 행이 길면 본문만 스크롤되고 footer는 남아야 한다
- 반응형 검수는 width뿐 아니라 height도 반드시 본다

## 5. footer는 컨테이너의 footer다

- table footer처럼 보이게 흉내내지 않는다
- 컨테이너 전체의 마지막 행으로 붙인다
- footer controls는 우측 하단에 모은다
- 페이지가 1개면 페이지 번호는 숨긴다
- 페이지 크기 선택기는 plain text처럼 가볍더라도 control 신호는 분명해야 한다

## 6. 버튼과 액션은 baseline이 맞아야 한다

- 버튼은 같은 행에서 기준선이 맞아야 한다
- 드롭다운, 검색창, 생성 버튼 높이와 정렬이 흔들리면 안 된다
- 필터와 액션은 같은 문맥 안에서 정렬돼야 한다
- footer controls도 text, button, select의 baseline이 맞아야 한다

## 7. 검색과 필터는 과장하지 않는다

- 검색 영역을 위해 별도 장식 컨테이너를 만들지 않는다
- 필터와 검색은 필요한 만큼만 나열한다
- 검색창 폭은 화면을 먹지 않게 제한한다
- 결과 수와 필터 정보는 필요한 위치 한 곳에만 둔다

## 8. 전역 CSS를 함부로 건드리지 않는다

- 한 페이지를 맞추려다 다른 페이지 헤더나 레이아웃을 깨뜨리면 실패다
- 공통 수정이 필요하면 먼저 템플릿이나 명시적 클래스 축으로 올린다
- 꼭 필요한 경우에도 적용 범위는 클래스 하나로 제한한다

## 9. 기존 화면은 구조보다 정렬부터 고친다

- 기존 운영 화면을 손볼 때는 구조 재조합부터 시작하지 않는다
- 먼저 정렬선, 간격, 카드 크기, 라벨 순서, 버튼 위치를 바로잡는다
- 사용자가 구조 변경을 원하지 않으면 `합치기`, `섹션 분리`, `새 요약 영역 추가`를 임의로 넣지 않는다
- 특히 모바일 보정은 구조를 바꾸지 않고 spacing과 width 반응형만 먼저 맞춘다

## 10. 목록형 편집은 읽기 모드와 수정 모드를 분리한다

- 목록 행은 기본적으로 compact read-only 상태로 둔다
- 입력 필드와 저장 버튼을 항상 열어 두지 않는다
- `수정`을 눌렀을 때만 같은 카드 하단에 edit panel이 열리게 한다
- `저장`과 `취소`는 panel을 다시 접어 읽기 모드로 돌아가야 한다
- 변경이 없어도 `저장`은 panel을 닫는 정상 동작을 해야 한다

## 11. 이벤트 로그는 상단 템플릿으로 올린다

- page body 안쪽에 `form-success`, `form-error`를 따로 남기지 않는다
- 성공/오류/주의 메시지는 상단 이벤트 로그 템플릿으로 올린다
- 본문은 입력과 작업만 남기고, 상태 메시지 때문에 카드 높이가 흔들리지 않게 한다

## 12. 순서 편집은 drag 느낌과 저장 모델이 같이 있어야 한다

- drag handle이 있으면 사용자가 실제로 카드를 잡았다는 피드백이 보여야 한다
- 드래그 중에는 원본 카드가 빠진 자리와 drop preview가 같이 보여야 한다
- 마지막 카드 아래로 이동하는 자리도 명시적으로 보여야 한다
- 그리고 backend에는 `display_order`처럼 순서를 저장하는 명시적 필드가 있어야 한다
- 프런트 미리보기만 있고 순서 저장 모델이 없으면 운영 기능으로 닫지 않는다

## 구현 전 체크

- 이 규칙이 template로 올라가야 하는지 먼저 본다
- 중복 정보가 생기지 않는지 먼저 본다
- footer가 container bottom인지 먼저 본다
- 반응형 검수에 height가 포함되는지 먼저 본다
- 버튼과 필터 baseline이 맞는지 먼저 본다
